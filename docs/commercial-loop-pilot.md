# 共同商业 Loop：真实 OpenCode 电商试跑

日期：2026-10-05。此次目标是改善 Runtime，再用真实 OpenCode 开发所选电商项目，发现并修复 Loop 问题。
这是有限压力实验，不是整个电商已经商业化的声明。原项目只读；实验在独立复制仓库与 worktree 中运行。
公开报告只保留 Runtime 结果与产品行为摘要，不上传电商源码、订单令牌、登录凭证或完整私有日志。

## 实际运行

- 工作平台：原生 OpenCode，模型 `opencode-go/deepseek-v4.1-flash`。
- 对标/阶段独立审核：原生 DSH；候选独立代码/安全审核另行运行。
- 输入：商业使用目标、成功标准、权限、真实源码及 Host 测试；没有提供执行 TODO 顺序。
- 参考来源：Saleor Storefront、Next.js Commerce、Shopify 货币语义、W3C 表单标签文档。
  Host 读取文档，模型检查适用性；URL 本身不计作验证。
- 分析与 Builder 总结允许自由文本；只有有限执行边界与审核结论有机器契约。

OpenCode 最初优先关注商品发现。独立审核指出遗漏的订单详情限制、未经验证的数据层假设和货币判断的夸大。
重新分析后，它自己把 localStorage 限制的订单详情提升为优先行动，而非继续原来的商品发现任务。
实际修改了 4 个前端文件，补充订单令牌链接、重新读取订单、登录订单回退和失败状态。

## 实验暴露的问题与修复

| 实测问题 | 处理 |
| --- | --- |
| 大段 JSON 上下文只有一行，OpenCode ReadTool 截断了尾部当前测试事实 | 按字节数、行长度和行数拆为多个有序附件；真实 192078 字节输入成功读取尾部标记 |
| 初步差距分析 PARTIAL 就终止 Loop，不能让后续决策消化反馈 | 初步分析作为决策输入；计划、执行路线、候选和最终完成仍有强制 Gate |
| 原压力实验的过期环境约束仍写着 Docker/Saleor 不可用 | 修正独立实验配置，并提供当前实际环境与 API schema |
| 计划、Builder 没有同等获得 Host 接口观察 | Builder 提示同时携带 Host 观察与接口契约，并新增回归断言 |
| Builder 已改代码，却因自然语言总结不符合旧 JSON 模板而报错 | 商业模式 Builder 使用自由文本；Host 用真实差异、测试、commit 与独立审核决定接受 |
| 原浏览器脚本把带查询参数的订单 URL 和历史链接误判为失败 | Host 按 URL path 判断订单号并允许合法查询参数；没有移除原行为检查 |
| 旧浏览器覆盖没有验证空设备订单详情，也漏了部分 GraphQL 契约 | 增加真实空上下文订单读取证据与实际 Saleor schema 文档校验 |

原生 ReadTool 限制依据 [OpenCode 源码](https://github.com/anomalyco/opencode/blob/dev/packages/opencode/src/tool/read.ts)。
传输修复保留权限边界，没有通过扩大外部目录读取权限绕过附件限制。

源码独立 Pi 审核还发现并推动修复：无预设参考时 Host 研究回调不执行、计划 Reviewer 未排除未来 Builder、
重启后贡献者身份变化导致排除不足、自由文本首尾空白丢失、公开抓取允许部分保留 IPv4 地址。
最终 Runtime 全量测试 62/62，通过原生 Pi 复审；证据见 [Runtime 验证记录](validation/commercial-runtime.json)。

## 验收边界

原生模型确实完成了代码修改，Host 在隔离环境运行后端测试、生产构建、严格 TypeScript 和桌面/移动浏览器购买流程。
新增空浏览器上下文读取证明实际调用了 Saleor `orderByToken` 并得到对应订单，不能用 localStorage 回填伪装成功。

这里有一次明确的 Host 人工介入：旧 Builder 结果解析失败后，代码留在未审核 worktree。
确认进程已经停止，再由 Host 封存候选并调用原 Runtime 的强制审核。
这不能称为已经证明“任意平台异常后全自动恢复”；新增自由文本修复通过回归测试与源码审核，尚未进行第二次全程无人干预实验。

接口检查还区分了两类问题：

- 当前 Saleor 的 `orderByToken` 查询有效；`order(token:)` 参数无效。候选包含可用路径及无效的兼容回退。
- 扩展覆盖发现基线已有的购物车删除响应 `lineId` 字段不兼容。旧浏览器用例没有覆盖删除，不能把它算成此次修改新引入的回归。

整份候选必须接受实际契约检查和独立审核；新功能部分有效不等于所有验收通过。
最终结论、测试与原项目完整性检查见 [电商试跑结果](validation/commercial-ecommerce.json)。

最终候选为 **REJECTED**：商业审核 REGRESSION，DSH 安全/代码审核拒绝，Pi 代码审核拒绝。
浏览器 36/36 通过，Builder 和干净提交树的 Host 聚合检查仍因契约错误失败，acceptedHead 没有推进。
DSH 还提出 URL 中能力令牌的引用来源策略与日志处理风险；这是待修复/验证项，不能宣称已验证安全上线。
原项目 294 个文件的哈希检查没有变化；电商候选保留在隔离工作树，没有自动合并。

## 后续重点

先补每个项目的真实接口、核心流程与异常路径覆盖，再扩展对标范围。
不应因为参考项目提供某功能，就假设当前部署支持同样接口；也不应因旧测试全绿，就宣布新的用户流程已验证。
完整搜索/视觉研究、所有平台不可用后的自动续写、真实支付与生产运营、长期无人值守仍需独立验证。
