# DSH Web 产品与 UI 对齐基线

2026-10-05。本文是下一阶段的实施与验收基线，不是已完成的 UI 验收报告。
当前默认方向：项目控制台为主、Agent 工作台为辅；用户可以指定其他参考产品。

## 参考依据

主参考为 [LangSmith Studio 官方文档](https://docs.langchain.com/langsmith/studio)：运行可视化、线程管理、状态调试与图/聊天两种模式。
借鉴其把执行过程与检查面板分开的产品模式；本文尚未完成该产品当前视觉界面的截图审计，因此不声称像素级对齐。

[OpenHands 官方使用指南](https://docs.openhands.dev/openhands/usage/get-started/tutorials)作为已有仓库、目标、变更检查的工作流程参考。
其当前文档将 Local GUI 列为 Deprecated Projects，不把旧 GUI 当作当前商业产品视觉标准。

参考用于形成自己的信息架构和验收标准。若复用第三方组件或源码，实施前检查具体版本与许可证并保留要求的声明。

## 现状与差距

依据 `web/index.html`、`web/app.js`、`runtime/server.mjs` 的实际源码审计。

| 用户流程 | 当前实现 | 对齐目标 | 优先级 |
| --- | --- | --- | --- |
| 连接项目 | 手写 JSON，CLI 启动；UI 只有说明 | 接入引导与配置校验，明确目标、标准、权限和测试命令 | 第二批，需要配置 API |
| 理解当前运行 | 一个长页面，阶段条、Gap、当前行动 | 总览显示当前问题、选择依据、执行阶段、最近失败和下一步 | 第一批，现有 API 可支撑 |
| 检查单次行动 | 行动表，证据按钮独立列出 | 选择行动后看到本次与累计 diff、测试、审核、commit、日志 | 第一批，部分证据需补映射 |
| 检查审核 | Reviewer/verdict 文本，JSON 原文 | 结构化 findings、阻塞原因、证据，原文按需展开 | 第一批 |
| 处理失败 | 状态和错误文本，CLI 恢复 | 明确失败类型、是否自动重规划、可执行恢复步骤 | 第一批显示；恢复操作需后端支持 |
| 运行控制 | 启动、边界暂停、取消、行动预算 | 状态敏感控制、请求中反馈、暂停语义、取消确认 | 第一批 |
| 观察 Agent | 四张状态卡，角色/权限/历史成功率 | 展示真实能力、身份、最近错误、当前隔离状态 | 第一批；实时余额需要供应商接口 |
| 项目交付 | acceptedHead 和 commit 文本，主 checkout 不合并 | 候选交付摘要、验证清单和人工检查步骤 | 第一批；自动合并不是现有功能 |
| 多项目与历史 | 单个配置运行时，单项目状态 | 项目切换、运行归档和历史查阅 | 后续，需要持久化与 API 扩展 |

## 第一批页面与交互

保留本地运行定位。导航改为总览、行动、审核与证据、Agents；不把它们只做成同一长页面的锚点。

总览：目标与成功标准 → 当前运行阶段 → 最大 Gap 与选择依据 → 最近行动和阻塞原因。
行动：可筛选的记录列表 + 选中行动检查面板。检查面板按概况、变更、测试、审核、日志分栏。
证据：明确标识本次 delta、累计 candidate diff、Builder 测试和干净 commit 测试。
审核：显示 Builder 与 Reviewer 身份、风险、verdict、blockingRisks 和 findings；审核通过不能覆盖测试失败。
Agents：保留 provider 可用性与实际运行记录。尚未配置或没有额度数据时显示未知，不填演示值。

不增加假的项目列表、聊天发送、合并、余额查询或恢复按钮。每个可点击控件必须有真实行为；
需要后端新增能力的项在产品计划中记录，不包装成已经可用。

## 视觉规范

目标用户是同时检查项目进展与候选质量的开发者。页面的主要任务是判断是否需要介入、以及候选是否可交付。

延续当前蓝灰控制台方向：背景 `#e9eef4`、面板 `#ffffff`、正文 `#182b43`、次级文字 `#617187`、
主操作 `#285fea`、通过 `#007e78`；失败沿用 `#b73e47`。状态必须同时有文本，不能只靠颜色。
中文正文使用 Segoe UI/Microsoft YaHei，标题使用 Bahnschrift，commit/耗时使用 Cascadia Code/Consolas。
字号、间距、边界与状态样式由统一 token 驱动。

桌面采用导航 + 主区域 + 行动检查面板，移动端改为列表到详情的单列流。
特色元素保留强制审核阶段：展示真实生命周期，而非装饰性流程图；其余页面保持克制。

## 验收要求

1. 新用户能从未配置状态找到具体接入步骤；启动按钮不能误导为已经连接项目。
2. 运行中能够辨认当前 Builder/Reviewer、行动目标、状态与权限。
3. 点击任何行动，证据只对应该行动；日志和报告使用文本渲染，不能执行其中的 HTML。
4. 拒审、额度不足、进程失败、NO_CHANGE、HALTED 与 MERGE_READY 显示不同解释。
5. MERGE_READY 显示候选已验收，不能声称主分支已合并；健康评分注明为模型评估，不作为验收通过率。
6. SSE 断线显示连接状态，保留已有信息；控制请求有等待/失败反馈，避免重复提交。
7. 覆盖未配置、空记录、运行、暂停、失败、拒审、完成的真实状态或明确标注的测试 fixture。
8. 390px 与 1440px 浏览器检查，主体无水平溢出；键盘能操作导航、列表和检查面板，焦点可见。
9. UI 对标需要参考截图、实现截图和功能行为证据；文档参考与截图审计分开记录。
10. 视觉完成不能替代后端能力验收，也不改变强制独立 Review Gate。
